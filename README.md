## Постановка задачи

Энергоснабжающие организации несут значительные потери из-за неисправностей счётчиков, несанкционированного потребления и сбоев в передаче данных. Ручная проверка тысяч интеллектуальных счётчиков нерентабельна.

Данный проект создаёт автоматизированный ML-пайплайн, который:

- **Классифицирует** счётчики по типу потребителя на основе признаков временного ряда
- **Обнаруживает аномалии** в профилях потребления методами обучения без учителя
- **Оценивает риск** каждого счётчика по шкале 0–100 с объяснимыми причинами
- **Кластеризует аномалии** по интерпретируемым типам («неисправность счётчика», «несанкционированное потребление» и др.)
- **Прогнозирует** вероятность перехода счётчика из нормального состояния в аномальное

Пайплайн обрабатывает **7 573 счётчика** в **16 классах потребителей** с интервалом измерений 30 минут за период октябрь 2024 — март 2025.

## Обзор пайплайна

Основной пайплайн (`main.py`) состоит из 14 последовательных шагов:

```
ШАГ 1   Загрузка и очистка данных       DatasetLoader + PowerSignalsFixer
ШАГ 2   Извлечение признаков            Статистические + FFT + электрические признаки
ШАГ 3   Разведочный анализ данных       EDAAnalyzer
ШАГ 4   UMAP-визуализация               Разделение классов потребителей в 2D
ШАГ 5   Классификация (Random Forest)   Предсказание класса потребителя
ШАГ 6   Анализ классификации            Матрица ошибок, важность признаков
ШАГ 7   Профили потребления             Почасовые и понедельные профили на счётчик
ШАГ 8   Признаки для аномалий           CV, энтропия, zero_ratio, peak_factor и др.
ШАГ 9   Isolation Forest                Разметка аномалий без учителя
ШАГ 10  UMAP для аномалий               2D-проекция пространства аномалий
ШАГ 11  Риск-скоринг                    Взвешенная оценка 0–100 + объяснение причины
ШАГ 12  Отчёты по топ-аномалиям        Временной ряд счётчика vs эталон класса
ШАГ 13  Кластеризация типов аномалий   KMeans + правила интерпретации кластеров
ШАГ 14  Модель переходов (норма→аномал) RandomForest: P(нормальный → аномальный)
```

После завершения пайплайна запускается веб-дашборд:

```bash
uvicorn app:app --reload --port 8000
```

### Типы аномалий (Шаг 13)

Аномальные счётчики группируются в интерпретируемые категории методом KMeans по поведенческим признакам. Метка кластера определяется правилом: признак с максимальным |z-score| в центроиде задаёт тип.

| Тип | Ключевой признак | Интерпретация |
|-----|-----------------|---------------|
| Неисправность / сбои передачи данных | `large_gap_ratio`, `max_gap_hours` | Аппаратный сбой или потеря связи |
| Несанкционированное потребление | `night_day_ratio` | Аномально высокая ночная нагрузка |
| Нестабильный режим потребления | `cv`, `entropy` | Хаотичный, непредсказуемый паттерн |
| Длительные простои / отключение | `zero_ratio` | Объект простаивает или отключён |

> Названия типов — это гипотезы для проверки инженером, а не финальный диагноз. Модель указывает направление расследования, а не ставит вердикт.

### Формула риск-скора

Риск-скор (0–100) — это взвешенная сумма четырёх нормализованных компонент:

```
Risk Score = 0.40 × norm(anomaly_score)     # Сигнал Isolation Forest
           + 0.20 × norm(cv)                # Нестабильность потребления
           + 0.20 × norm(night_day_ratio)   # Ночная активность
           + 0.20 × norm(max_gap_hours)     # Разрывы в передаче данных
```

### Модель переходов (Шаг 14)

Временной ряд каждого счётчика разбивается на два равных периода по времени. Признаки из Периода 0 (первая половина) используются для предсказания, будет ли Период 1 (вторая половина) аномальным — **сигнал раннего предупреждения**.

- Разбивка train/test: по `meter_id` (тестовые счётчики целиком не видны при обучении)
- Дисбаланс классов: ~5% положительных примеров — переходов в аномалию
- Модель: `RandomForestClassifier(class_weight='balanced')`
- ROC-AUC на удержанных счётчиках: **0.90**

##  Веб-дашборд

Приложение `app.py` на FastAPI читает результаты пайплайна и предоставляет интерактивный интерфейс мониторинга для операторов управляющей компании.

### Страницы

**`/` — Обзор счётчиков**
- Сводная статистика: всего счётчиков, аномалий, высокий риск, средний Risk Score — с тултипами-объяснениями
- Фильтры: класс потребителя, диапазон Risk Score, только аномалии
- Сортируемая таблица: клик по заголовку **Risk Score** или **Anomaly Score** меняет порядок
- Пагинация по 50 записей

**`/meter/{id}` — Карточка счётчика**
- Risk Score с цветовым индикатором и тултипом
- Anomaly Score (IF) с тултипом
- Вероятность перехода в аномалию (только для нормальных счётчиков — для аномальных не отображается, так как модель обучалась на первой половине, когда счётчик ещё был нормальным)
- Диагностика: тип аномалии + главная причина риска
- **Интерактивный временной ряд** с:
  - Выбором вида энергии: A+, A-, R+, R-
  - Пресетами периодов: весь период / последний месяц / последняя неделя / первый месяц / первая неделя / другое
  - Выбором произвольного диапазона дат через календарь (включая один конкретный день)
  - Автоматическим масштабом: сырые точки для ≤2 дней, по суткам для ≤31 дня, по неделям для ≤4 месяцев, по месяцам для более длинных периодов
- **График по дням недели** с теми же фильтрами (независимый блок)

**`/risk` — Карта рисков**
- Scatter-plot: Risk Score vs Anomaly Score (все 7 573 счётчика, раскраска по уровню риска)
- Столбчатый график: средний Risk Score по классам потребителей
- Гистограмма: распределение вероятности перехода в аномалию (только нормальные счётчики)
- Таблица топ-30 аномальных счётчиков с типом аномалии и главной причиной

### Производительность

- **Индекс при старте**: при запуске `app.py` читает только колонку `device_id` из каждого raw-файла и строит словарь `meter_id → файл`. Полные данные не грузятся.
- **LRU-кэш**: до 200 временных рядов счётчиков в памяти — повторный заход на карточку мгновенный.
- **API-эндпоинты**: данные для графиков отдаются через `/api/meter/{id}/timeseries` и `/api/meter/{id}/weekday-stats` — смена фильтров не перезагружает страницу.

##  ML-методы

### Извлечение признаков (Шаг 2)

Для каждого счётчика извлекается ~50 признаков из сырого временного ряда по четырём видам энергии (A+, A-, R+, R-):

- **Статистические**: среднее, std, мин/макс, медиана, 5-й/95-й перцентили, CV
- **Частотные (FFT)**: максимальная амплитуда спектра, среднее спектра, спектральная энергия
- **Электрические**: полная мощность (|A + jR|), фазовый угол

### Классификация потребителей (Шаг 5)

`RandomForestClassifier(n_estimators=300)` обучается на 50 признаках с разбивкой 80/20 со стратификацией. UMAP-проекция (Шаг 4) подтверждает хорошую разделимость классов в пространстве признаков.

### Обнаружение аномалий (Шаг 9)

`IsolationForest(contamination=0.03)` на 7 компактных признаках (CV, энтропия, доля нулей, peak factor, load factor, среднее, std). Значение `contamination=0.03` обосновано распределением `anomaly_score` — точкой перегиба на отсортированной кривой скоров.

### Кластеризация типов аномалий (Шаг 13)

KMeans (k=4) на тех же 7 признаках плюс `night_day_ratio`, `max_gap_hours`, `large_gap_ratio` из профилей потребления. Признаки масштабируются `RobustScaler` (медиана/IQR), а `night_day_ratio` и `max_gap_hours` предварительно winsorize по 1–95-му перцентилю, чтобы 1–2 экстремальных выброса не доминировали в масштабировании.

### Модель переходов (Шаг 14)

Временной ряд каждого счётчика разбивается на два равных периода по времени. Признаки первого периода предсказывают, будет ли второй период аномальным (разметка — отдельный Isolation Forest на признаках периодов). Train/test разбивается по `meter_id`: данные тестовых счётчиков полностью скрыты при обучении — оценка отражает обобщение на новые объекты, а не интерполяцию по времени.

## Эксперименты и выводы

**Почему «нормальный» счётчик может иметь ненулевой Risk Score?**

Risk Score — непрерывная метрика 0–100, а метка Isolation Forest — бинарная (при `contamination=0.03`). Счётчик может быть «нормальным» по порогу IF, но при этом иметь повышенный `night_day_ratio` или `cv`, которые вносят вклад в Risk Score. Это отражает бизнес-реальность: не каждый подозрительный паттерн пересекает порог детектора, но операторам всё равно стоит обратить на него внимание.

**Почему визуально похожие счётчики получают разные метки аномалии?**

Isolation Forest чувствителен к абсолютному масштабу значений, а не только к форме профиля. Счётчик с пиком 400 единиц на нулевом фоне редко встречается среди 7 573 счётчиков и быстро изолируется. Счётчик с аналогичным паттерном на уровне 0.25 единиц имеет много «соседей» и не считается редким. Это одновременно сильная сторона (ловит экстремальные выбросы) и ограничение, которое стоит учитывать при интерпретации результатов.
